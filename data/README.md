# Data

Released corpora, their provenance, and pointers to the third-party and attack
material that is not redistributed.

```
data/
├── benign/
│   ├── controlled/     benign traffic for the two controlled applications (rule admission)
│   └── external/       benign traffic for the external targets (bWAPP, Juice Shop)
├── scripts/            corpus construction and validation code
├── third-party/        CSIC / Torpeda 2012: citation, retrieval, checksums (not redistributed)
└── attack-corpora.md   why no attack payloads are released, and what is instead
```

## Benign corpora (released)

Every file is a list of complete benign HTTP requests, one per line. All were
generated by us from curated templates and benign vocabularies (random usernames,
passwords, product-search terms, arithmetic), not drawn from any third-party set,
so redistributing them is unproblematic.

### Controlled applications (rule-admission corpora)

| File | Requests | Target / context |
| --- | --- | --- |
| `benign/controlled/sqli_admission_benign.txt` | 2,000 | controlled SQLi app (login, search, product, filter) |
| `benign/controlled/xss_admission_benign.txt` | 2,000 | controlled XSS app (search, calculator) |

These are the corpora against which the cumulative 1% false-positive gate is
enforced during rule admission.

### External targets (generalization corpora)

| File | Requests | Target / context |
| --- | --- | --- |
| `benign/external/bwapp_sqli_login_benign.txt` | 1,000 | bWAPP SQLi login |
| `benign/external/bwapp_sqli_search_benign.txt` | 1,000 | bWAPP SQLi search |
| `benign/external/juice_sqli_login_benign.txt` | 1,000 | Juice Shop SQLi login |

## How the benign corpora were validated

Two independent checks, in this order:

1. **Application backend.** `scripts/check_benign.py` (and `check_benign_juice.py`
   for Juice Shop) sends each request to the application with no WAF and reads an
   inline oracle. A request is kept as benign only if it produces no SQL error, no
   crash, no unexpected login success, and no full-table dump. Anything else is
   excluded with a recorded reason.

2. **Baseline CRS.** The kept requests were replayed through baseline ModSecurity +
   CRS (CRS only, before any generated rule). **Every released benign request was
   confirmed to pass baseline CRS**, so a later false positive is attributable to a
   generated rule, not to CRS or to a mislabeled request.

## Construction and validation scripts

| Script | Role |
| --- | --- |
| `scripts/generate_controlled_benign.py` | build the controlled-app benign corpora from templates |
| `scripts/generate_external_benign.py` | build the bWAPP / Juice Shop benign corpora |
| `scripts/check_benign.py` | backend validity check for the controlled app |
| `scripts/check_benign_juice.py` | backend validity check for Juice Shop |
| `scripts/csic_preprocess_replay.py` | replay third-party CSIC normal requests through CRS (preprocessing for the fallback) |

These scripts contain no attack-generation logic and were scanned for credentials
before release.

## Third-party data (not redistributed)

The CSIC / Torpeda 2012 dataset is not included. Its normal partition is the
external CSIC benign corpus (8,363 requests) and its anomalous partition is a
non-LLM attack source. `third-party/csic-torpeda-2012.md` gives the citation,
retrieval steps, the checksums of the versions we processed, the record counts,
and the preprocessing command, so the exact inputs can be reconstructed.

## Attack payloads (not released)

No attack payloads are published, by design. `attack-corpora.md` explains what is
released instead (counts, outcomes, aggregate statistics under `results/`) and how
to reproduce each attack source.
