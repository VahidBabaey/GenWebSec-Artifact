# Pre-release security audit

A whole-repository sweep confirming that none of the material the artifact
specification prohibits was released, and documenting what is deliberately withheld
so its absence is not mistaken for an incomplete artifact.

## What was scanned

Every file in the repository (209 files) was scanned line by line for five
categories of prohibited content:

| Category | Result |
| --- | --- |
| API keys, auth tokens, provider credentials | **0 found** |
| passwords / secrets with values | **0 found** |
| raw attack payloads (outside defensive rule signatures) | **0 found** |
| private infrastructure / machine-specific identifiers | neutralized (see below) |
| attack-agent prompts or prompt-reconstructing fragments | **0 found** |

The scan and its patterns are in the build tooling; it is re-runnable before any
future release.

### Attack payloads vs. defensive signatures

The released ModSecurity rules (`rules/`, `scripts/`) intentionally contain SQL and
JavaScript *tokens* (for example `select`, `case when`, `alert`, `eval`, comment
operators) because they are detection signatures, which is the whole point of the
artifact. The payload scan distinguishes these from usable attack payloads and
excludes `SecRule`/`@rx` signature lines; it found no raw attack payload anywhere in
the repository.

### Machine-specific paths (neutralized)

The released aggregators, evaluation scripts, and non-LLM processing scripts
originally hard-coded an absolute working-directory path that contained a username.
Every occurrence was replaced with the neutral placeholder `/path/to/GenWebSec`
across 27 files. The runnable analysis scripts (`analysis/`) never used absolute
paths; they resolve everything relative to the repository.

### Residual, intentional identifiers

Three items match the identifier patterns and are kept on purpose:

- the authors' institutional email addresses in `CITATION.cff` and `SECURITY.md`
  (author identification / security contact);
- a `C:\Users\<user>\...` **placeholder** (not a real username) in the `.wslconfig`
  example in `environment/hardware.md`;
- the WSL kernel version string `6.6.87.2`, which superficially resembles an IP
  address but is a version number.

## What is deliberately withheld, and why

Per the specification, the following are not in the repository. Each is documented
where a reader would look for it, so the omission reads as a safeguard, not a gap.

| Withheld | Reason | Documented in |
| --- | --- | --- |
| Attack-agent prompts | operational guidance for generating WAF-bypassing payloads | `prompts/attack/README.md` |
| Attack-only and co-evolution driver scripts | drive attack generation; import the withheld prompts | `scripts/attack/README.md` |
| Raw generated bypass payloads | dual-use; released as counts/outcomes instead | `data/attack-corpora.md` |
| Raw run logs (verbatim) | contain payloads inline; released in sanitized form | `logs/README.md` |
| CSIC / Torpeda 2012 dataset | third-party; not redistributed | `data/third-party/csic-torpeda-2012.md` |
| sqlmap / Dalfox payload sets | generated by third-party tools; not redistributed | `data/attack-corpora.md` |
| Exact defense-prompt worked examples | redacted from the released prompts | `prompts/defense/README.md` |

Provenance checksums for the withheld attack corpora and the third-party datasets are
in `manifests/provenance_checksums.csv`, so a reviewer can confirm they reconstructed
the same inputs without those inputs being released.
