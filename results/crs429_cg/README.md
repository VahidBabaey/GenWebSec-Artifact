# Co-evolved rules vs CRS-4.29 held-out bypasses

Supports the manuscript tables `tab:crs429-cg-sqli` (SQLi) and `tab:crs429-cg-xss`
(XSS), which accompany reviewer comment R1.3. The updated OWASP CRS 4.29.0 still
leaves a residual attack surface (reported in `../updated_crs/`); these tables
show that the frozen co-evolved rules close that residual. No rule generation
happens here: the frozen CG-Adaptive and CG-Static rulesets are replayed against
held-out attacks that bypass CRS 4.29.0.

This directory is **payload-free**. The per-attack replay logs reference attack
payloads, so they are not released; the released matrices are counts and rates
only.

## Held-out attacks and shifts

The held-out sets are generated SQLi/XSS winners that are backend-valid AND
bypass OWASP CRS 4.29.0. Each target page has five independent attack seeds, and
each attack seed is replayed against ten frozen defense seeds (5 x 10).

| Target | Backend | Held-out attacker | Shift |
| --- | --- | --- | --- |
| customapp | Python/SQLite | Claude Opus 4.7 | model shift (same app) |
| customxss | PHP | Claude Opus 4.7 | model shift (same app) |
| bwapp | PHP/MySQL | Llama-4 Maverick | cross-backend |
| juice | Node.js/SQLite | Llama-4 Maverick | cross-backend |

## Two evaluation modes

- **SQLi, `crs429_cg_sqli_matrix.csv` (`tab:crs429-cg-sqli`)** -- the co-evolved
  rules run WITH CRS 4.29.0 deployed. Eight target pages. The held-out sets are
  CRS-4.29 bypassing by construction, so the CRS-only baseline over them is near
  zero and the reported rate is essentially the co-evolved rules' contribution.
- **XSS, `crs429_cg_xss_matrix.csv` (`tab:crs429-cg-xss`)** -- the co-evolved
  rules run in ISOLATION (CRS disabled), so the reported rate is the generated
  rules' own coverage of the CRS-4.29 bypasses. Three target pages.

## Columns

| Column | Meaning |
| --- | --- |
| `family` | SQLi or XSS |
| `target`, `page` | the target application and page (customapp `product` is the "URL parameter" page) |
| `shift` | `model_shift` (customapp/customxss) or `cross_backend` (bwapp/juice) |
| `strategy` | CG-Adaptive or CG-Static |
| `attack_seed` | `1`..`5` for a held-out attack seed, or `aggregate` for the per-page summary |
| `mean_block_rate_over_defense_seeds` | per seed: block % averaged over the 10 defense seeds; aggregate row: mean over the 5 seeds |
| `sd_over_attack_seeds` | aggregate row only: sample SD (n-1) across the 5 attack-seed values |
| `blocked_sum`, `total_attacks` | counts pooled over the 10 defense seeds (per-seed row) or over all 5 x 10 replays (aggregate row) |

## Cell aggregation

For each attack seed, average the block rate over the ten defense seeds (one
value per seed); then report mean +/- SD across the five attack-seed values. The
SQLi cross-backend summary is a count-pooled micro-average (sum blocked / sum
total over the four cross-backend pages); the XSS summary is a macro-average over
the three pages. The `aggregate` rows carry the same per-page summary that the
analysis script recomputes from the per-seed rows.

## Reproducing the tables

```
python analysis/crs429_cg_replay.py
```

Verified against the manuscript:

- SQLi (CG-Adaptive / CG-Static): Custom Login 100.0/90.1, Custom Search
  100.0/100.0, Custom URL parameter 100.0/100.0, Custom Filter 99.9/99.9,
  bWAPP Login 100.0/96.3, bWAPP Search 100.0/93.6, Juice Login 100.0/97.0,
  Juice Search 100.0/90.0; cross-backend micro-average 100.0/94.1.
- XSS (isolation): Custom Search 100.0/100.0, Custom Calculator 85.9/85.2,
  bWAPP eval sink 88.3/87.4; macro-average 91.4/90.9.
- CG-Adaptive blocks 100% of every held-out SQLi set; CG-Static leaves a small
  residual on the model-shift and cross-backend logins. On the eval-sink XSS
  pages the two strategies agree within about one point.

## Notes

- Standard deviations are sample SD (n-1) across the five attack seeds; a cell at
  100.0 with SD 0.0 means every seed blocked every held-out attack.
- The held-out attacks are generated by the withheld CRS-4.29 attack-prompt
  modules (hashes in `../../manifests/provenance_checksums.csv`); the CRS-4.29
  drivers live in `../../scripts/updated_crs/`. Like the other drivers in this
  artifact, the defense-replay step imports the withheld attack modules and reads
  the frozen held-out attack files at run time.
- The attack-surface persistence of CRS 4.29.0 itself (before the co-evolved
  rules are applied) is in `../updated_crs/`.
