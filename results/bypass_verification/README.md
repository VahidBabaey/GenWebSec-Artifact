# Bypass-criterion re-verification (exploit-confirmation through the WAF)

> Layout note: in this repository the data lives here (`results/bypass_verification/`), the audit and
> access-log records referenced below as `waf_logs/` are in `logs/bypass_verification/`, and the
> generating scripts are in `scripts/bypass_verification/`. See `manifests/bypass_verification.md`.

Reviewer 1.1 asks us to re-verify that an attack counted as a *successful WAF bypass* is a genuine,
working exploit delivered through the WAF, not merely a request that returns a non-403 status. This
folder holds the re-verification for RQ1 (attack generation) and RQ3 (co-evolution held-out stress),
both families (SQLi and XSS), computed directly from the saved runs — no sampling, no estimates.

The bypass criterion is two-stage:
* **Route A (backend, no WAF):** the attack is replayed against the custom app with no WAF in front;
  the exploit oracle confirms it actually works (SQLi: login/data oracle; XSS: a JS dialog fires in a
  real headless browser). This establishes `backend_valid`.
* **Route B (WAF):** the identical string is sent through the real WAF (Apache 2.4.52 +
  ModSecurity 2.9.5 + OWASP CRS 3.3.2, plus the run's frozen custom rules). Status 403 = blocked;
  otherwise the exploit is re-confirmed on the WAF-returned response (`valid_through_waf`). A request
  that is not-403 but whose exploit does **not** fire through the WAF is a *false bypass*.

## Part 2 — RQ3 (co-evolution held-out stress replay)

Each co-evolution run (eps0.3 for the clustered defense CG; per-payload PP has no eps) ends with a
held-out *stress* batch of fresh attacks tested against the run's frozen rule set. We re-loaded each
run's frozen rules and replayed its saved held-out attacks through the real WAF with the two-stage
criterion, then compared the recomputed funnel (valid / CRS-bypass / blocked-by-rules / still-bypass)
against the funnel the run logged.

### SQLi — full-funnel two-stage replay  (`rq3/`)
`scripts/r11_rq3_replay_sqli.py`, driven by `scripts/run_rq3_cg.sh` + `scripts/run_rq3_pp.sh`.
All 300 held-out attacks per run are re-classified under CRS-only then CRS+frozen-rules.
* Runs: 80 = {CG, PP} × {login, search, product, filter} × seeds 1–10 (CG = eps0.3).
* Funnel faithfulness: **80/80 runs reproduce the logged funnel exactly** (0 unfaithful).
* Residual (still-bypassing) attacks: **207** (PP 185, CG 22) — **all 207 re-confirmed as real
  exploits through the WAF**; **0 false bypasses**; reported block% == verified block% in every run.
Files: `rq3/rq3_sqli_summary.csv` (per-run funnel + verification), `rq3/rq3_sqli_perattack.csv`
(one row per held-out attack, payload hashed).

### XSS — valid+bypassed scope  (`rq3_xss/`)
`scripts/r11_rq3_replay_xss.py`, driven by `scripts/run_rq3_xss.sh`.
Scope (per the agreed design): re-check only the attacks the log marks backend-**valid** (re-confirm
each executes on the backend) and those that **bypass** (re-confirm each exploits through the WAF).
Non-executable and pure-CRS-blocked candidates are not claimed as successes, so they do not bear on
the criterion.
* Runs: 40 = {CG, PP} × {calc, search} × seeds 1–10 (CG = eps0.3).
* Valid held-out attacks: **5,392 — all 5,392 re-confirmed executing on the backend**.
* Residual (still-bypassing) attacks: **0** across all 40 runs (CRS + co-evolved rules blocked every
  valid held-out attack); hence **0 false bypasses**.
* Funnel faithfulness: 39/40 runs reproduce the logged funnel exactly. The one exception, **PP/calc
  seed 1**, re-measures CRS-bypass = 63 vs the log's 62 (and blocked-by-rules 63 vs 62). This is a
  single held-out attack sitting on the CRS anomaly-score boundary: re-measured 63/63/63 across three
  independent trials (`scripts/stab_pp_calc1.py`), so the run-time log's 62 was a transient (a
  momentary 403, e.g. mid-reload) while the steady-state CRS verdict is "bypass." That attack is still
  blocked by the co-evolved rules (not a residual), so CRS-bypass and blocked-by-rules move together
  and the **held-out block rate stays 100%** — RQ3/Table 6 reports rates, so the manuscript number is
  unaffected.
Files: `rq3_xss/rq3_xss_summary.csv` (per-run funnel + verification), `rq3_xss/rq3_xss_perattack.csv`
(one row per valid held-out attack, payload hashed).

### XSS execution-oracle note (disclosure)
The XSS data was generated with Selenium driving the system snap Chromium. On the replay host `snapd`
is masked, so the snap Chromium/Chromedriver will not launch. The replay therefore drives
**Playwright's bundled headless Chromium** instead (its one missing system library, `libasound.so.2`,
is supplied from the pre-staged Ubuntu-22.04 package under `~/tools/deps`). Both are headless Chromium
and return identical execution verdicts for these dialog-based payloads; this was confirmed before the
run on the calc eval-sink exploit and on real search string-breakout exploits, and is corroborated
by the 5,392/5,392 validity re-confirmation and the exact funnel reproduction.

## Part 3 — RQ4 (freeze-then-replay held-out, Tables 6–8)  (`rq4/`)

RQ4 freezes each target's held-out winner set (valid + CRS-bypassing) and replays it against every
per-seed rule set (CG-Adaptive from C1/C2, CG-Static from D1/D2), recording 403 vs non-403. The original
replay stored only the status; here we take the **residual bypasses** (non-403 under a defense rule set)
and re-probe each through the WAF with the exploit oracle (`pilot.probe` → status + exploit verdict),
reusing the same per-target oracle that generated the winners. Scope (agreed): residual bypasses under
CG-Adaptive + CG-Static at **eps0.3** (the Tables 6–8 config); CRS-only bypasses are the frozen winners,
already exploit-confirmed at freeze. Scripts `scripts/r11_rq4_reverify_sqli.py`,
`scripts/r11_rq4_reverify_xss.py`, `scripts/r11_rq4_reverify_xss_bwapp.py`.

Per-request outcomes (one row per re-probed bypass: target, page, technique, seed, attack index,
`payload_sha1`, `waf_status`, `exploit_through_waf`) are in `rq4/rq4_sqli_perrequest.csv` (13,167 rows)
and `rq4/rq4_xss_perrequest.csv` (3,073 rows); every row has `exploit_through_waf=1` (16,240 total,
0 false). The re-run reproduced the summary byte-for-byte.

Result (`rq4/rq4_sqli_summary.csv`, `rq4/rq4_xss_summary.csv`, consolidated in
`rq4/rq4_verification_summary.txt` via `scripts/sum_rq4_all.py`):

| Target | Residual bypasses | Re-confirmed real exploits | False bypasses | Reclassified (now 403) |
|---|---|---|---|---|
| customapp (SQLi) | 62 | 62 | 0 | 0 |
| juice (SQLi) | 2,652 | 2,652 | 0 | 0 |
| bwApp (SQLi: login 10,248 + search 205) | 10,453 | 10,453 | 0 | 0 |
| customxss (XSS) | 2,464 | 2,464 | 0 | 0 |
| bwApp (XSS: xss_eval) | 609 | 609 | 0 | 0 |
| **total** | **16,240** | **16,240** | **0** | **0** |

All four targets done. Every re-probe reproduced the original 403-vs-bypass classification (now_403 = 0),
so the Tables 6–8 block rates are unchanged and now effect-verified. For customapp/juice/customxss the
residuals concentrate under CG-Static (chiefly seed 10, the known weak-static-seed quirk) and CG-Adaptive
leaves few; bwApp is the hardest cross-backend case (customapp/customxss-trained rules match bwApp's
CASE-WHEN login and eval-sink attacks poorly, so many held-out attacks bypass) — but every one of those
bypasses is a genuine exploit (0 false). bwApp needed a one-time DB install (`install.php?install=yes`)
and a bee/bug session; its container start required `modprobe iptable_raw` + instantiating the legacy
raw table (`scripts/r11_rq4_reverify_xss_bwapp.py` handles the WAF-side login).

Scope note: this re-probes the residual bypasses under the CG defenses at eps0.3 (the Tables 6–8 config).
The CRS-only RQ4 baseline (the frozen winners) was exploit-confirmed at freeze; R1.6's recount of that
baseline found 21,459/21,466 confirmed and **7 Juice-Shop responses that returned HTTP 502 and are NOT
real exploits** — i.e. the exact error-not-exploit case the reviewer raised. Those 7 must be excluded
from the baseline bypass count and are positive evidence that the two-stage criterion works; reconcile
R1.1's "0 false bypasses" (scoped to CG residuals) with R1.6 in the response letter.

## Part 4 — WAF logs (item 5)  (`waf_logs/`)

`scripts/r11_audit_capture.py` enables `SecAuditEngine On` (via the vahid-writable `sft_rule.conf`, no
root) and replays a representative request set, capturing audit entries that distinguish blocking from
other responses: benign → 200 no rule; classic SQLi/XSS → 403 by CRS (942100 / 941xxx + 949110);
eval-sink `alert(1)` → 200 (a non-403 bypass, re-verified to execute); held-out winners → 403 by our
custom rule (id 1000001). The Apache access log corroborates the statuses and is readable here (the
account is in the `adm` group), so no root copy is needed. See `waf_logs/README.md`.

## Combined result
RQ1 + RQ3 + RQ4 all re-verify the two-stage criterion on the live WAF. RQ1: 9,159 SQLi + 2,892 XSS
non-403 bypasses, 100% exploit-confirmed through the WAF (all HTTP 200). RQ3: 120 runs, SQLi 207/207

## Independent audit
An adversarial multi-lens audit (numbers / methodology / completeness / oracle+redaction / skeptic +
synthesis) re-read the artifacts and recomputed every headline number from the raw CSVs: all match, 0
mismatches; the two-stage criterion is correctly implemented (genuine exploit re-reads, not status-only);
redaction holds (payloads only as sha1 / `<redacted>`). Verdict: sound. Remaining items it flagged are
the write-ups (manuscript two-stage restatement, RQ2 transfer argument) and reconciling the 7 Juice-502
baseline cases with R1.6 — all writing, no further compute. The oracle-swap (Playwright for snap Chromium)
and the PP/calc-seed1 funnel transient are disclosed and change no reported rate.

## Redaction
Raw attack payloads and attack prompts are withheld. Per-request/per-attack files identify each
payload only by `payload_sha1` (stable 16-hex). Outcomes, funnels, counts, and statuses are released
in full.
